\begin{abstract}
The performance of bandwidth-limited algorithms strongly depends on
compute memory hierarchy.  In this article, we propose a model for FFT
performance on ROCm GPUs as a function of shared memory (LDS) size and
performance.
\end{abstract}

\keywords{FFT, GPU, LDS, ROCm}

\section{Introduction}

the fast Fourier transforms (FFT) is considered one of the most
important algorithms of the modern era~\cite{strang1994wavelets} and
has a variety of important uses from digital signal
processing~\cite{sorensen1990efficient}, to computational fluid
mechanics~\cite{chatterjee2018scaling}, to machine
learning~\cite{mathieu2013fast}, and many others.  The FFT algorithm,
first fully developed in~\cite{cooley1965algorithm}, reduces the
computational complexity from $\mathcal{O}\(N^2\)$ to
$\mathcal{O}\(N\log{}N\)$, and the numerical error from
$\mathcal{O}\(\sqrt{N}\)$ to $\mathcal{O}\(\sqrt{\log{}N}\)$
~\cite{gentleman1966fast}.

The FFT is bandwidth-limited for all practical problem sizes on modern
hardware.  Moreover, the data dependency diagram is all-to-all; every
point of the output depends on every point of the input.  Effective
data movemnet is an imporant factor in designing high-performace FFT
implementations.  In this article, we explore how performance on SIMT
(single-instruction multiple thread) architectures such as the GPU,
and establish a theoretical performance model to help understand how
changes in local data share (LDS) size affects GPU FFT performance.


Bandwidth-limited algorithms such as the FFT can benefit greatly from
the improved bandwidth and reduced memory latency provided by data
caches, and the MI300 now contains three levels of
cache\footnote{\url{https://hipfft.readthedocs.io/en/rocm-6.1.2/reference/gpu-arch-specs.html}}.
Taking advantage of these different levels and sizes of cache is
labour-intensive, but this cost can be mitigated by making use of
cache-oblivious algorithms~\cite{frigo1999cache}.  On the other hand,
the LDS size has remained fixed at 64KiB on MI devices up to the MI300
series, while the NVIDIA V100 can be configured to have up to 96KiB,
the P100 up to 164KiB, and the H100 has 224KiB.  Due to the SIMT FIXME

\section{One-Dimensional Complex Transforms}
\label{section1d}
\subsection{Single-pass Transforms}

The discrete Fourier transform of the complex input
$\{f_\ell\}_{\ell=0}^{N-1}$ of length $N$ is
\begin{dmath}
  \label{dft}
  \{F_k\} = \sum_{\ell=0}^{N-1} e^{\frac{-2\pi{}ik\ell{}}{N}} \{f_\ell\}_{\ell=0}^{N-1}
\end{dmath}
which is denoted as $F = \mathcal{F}_N\(f\)$.  If the entirety of the
input fits into LDS, then the transform can be computed with just one
single pass to global memory.  This is more of less the optimal case
for FFTs on GPUs; if the batch size is large enough, we can saturate
the global memory bandwidth, but also avoid reading/writing to global
memory repeatedly.  Calls to \lstinline{__syncthreads} prevent
race-conditions when moving data between LDS and CU registers.  One
can reduce LDS requirements, allowing for more larger transforms or
increasing occupancy, by communicating the real and imaginary
components separately, though this comes at the expense of an
additional \lstinline{__syncthreads}.  Since the per-CU VGPR
register file for MI100/MI200/MI300 is 521KiB with LDS limited to
64KiB, it's theoretically possible to put up to eight times the LDS
size per CU, allowing for even larger single-pass transforms.
However, it's likely possible that some VGPRs will be used by other
parts of the algorithm (eg the twiddle tables), and there is a
tradeoff because increased synchronization and reduced occupancy must
be taken into account.

Strategies for different batch-sizes and optimizations objectives
should also be considered.  In particular, for a double-precision
complex FFT of length 512 with batch-size is 1, a latency-optimised
transform would benefit from having multiple threads work on the same
data; for larger batches (or, equivalently, throughput-optimised
transforms) one could theoretically load each individual 512-length
FFT into the VGPRs of a single SIMT thread.

More LDS allows for a larger range of single-pass FFTs. For
latency-optimised transforms, an increase in LDS reduces the number of
CU-level synchronizations.  Calls to \lstinline{__syncthreads},
while less costly than loads/stores to global memory, are still
relatively expensive.

Let $N$ be the problem size, $L_B$ be the size in bytes of the LDS
cache, and $T_S$ the size of the data type (eg
\texttt{sizeof(std::complex<double>)}, which is 16).  If $N T_s \leq
L_B$, then the problem fits into LDS.  This encurs just one
global-memory round-trip and one call to \lstinline{__syncthreads}.



\subsection{Multiple-Pass Transforms}

As problem size increases, the FFT will eventually not fit into the
memory accessible to a single CU.  For larger FFTs, it's necessary to
use global GPU memory to save intermediate results.  This technique
makes use of the basic technique for writing cache-aware FFTs relies
on the recursive decomposition inherent in the FFT algorithm, and was
first given in~\cite{bailey1990ffts}.  If $N=N_aN_b$, then consider
$F$ as a two-dimensional array by setting
\begin{dmath}
  \{F_k\}_{k=0}^{N-1}
  =
  \{F_{N_a k_b + k_a} \}_{\(k_a,k_b\)\in\{0,\dots,N_a-1\}\times\{0,\dots,N_a-1\}},
\end{dmath}
which allows one to decompose equation~\eqref{dft} as
\begin{dmath}
  \label{N1N2}
  F_{N_a k_b + k_a}
  =
  \sum_{\ell = 0}^{N-1} e^{\frac{-2\pi{}i\ell{}(N_a k_b + k_a)}{N}} f_\ell
  =
  \sum_{\ell_1 = 0}^{N_a-1}
  \sum_{\ell_2 = 0}^{N_b-1}
  e^{\frac{-2\pi{}i\(\ell_a N_b + \ell_b\)(n_a k_b + k_a)}{N}}
  f_{\ell_a n_b + \ell_a}
  =
  % FIXME: formatting
  % https://tex.stackexchange.com/questions/44450/how-to-align-a-set-of-multiline-equations?
  %% \sum_{\ell_1 = 0}^{N_1-1}
  %% \sum_{\ell_2 = 0}^{N_2-1}
  %% \cancelto{1}{e^{\frac{-2\pi{}i\(\ell_1 n_2 n_1 k_2 \)}{N}}}
  %% e^{\frac{-2\pi{}i\(\ell_1 n_2  k_1\)}{n}}
  %% e^{\frac{-2\pi{}i\(\ell_2n_1 k_2\)}{n}}
  %% e^{\frac{-2\pi{}i\(\ell_2 k_1 \)}{n}}
  %% f_{\ell_1 n_2 + \ell_2}
  %% =
  \sum_{\ell_2 = 0}^{N_a-1}
  e^{\frac{-2\pi{}i\ell_b k_b}{N_b}}
  e^{\frac{-2\pi{}i\ell_b k_a }{N}}
  \sum_{\ell_a = 0}^{N_a-1}
  e^{\frac{-2\pi{}i\ell_a k_a}{N_a}}
  f_{\ell_a N_b + \ell_b}.
\end{dmath}
we have used the fact that $e^{\frac{N_1N_2}{N}}=1$.  The length-$N_1$
and $N_2$ sums are themselves Fourier transforms; in fact, this
decomposition is exactly the heart of the FFT.  Note that the input
and output are contiguous in different indices.  We can express the
operation in equation~\eqref{N1N2} as
\begin{dmath}
  \mathcal{F}_{N_b}\[
  \{
  e^{\frac{-2\pi{}i\ell_b k_a }{N}}
  \mathcal{F}_{N_a}\[\{f_{\ell_a N_b + \ell_b}\}_{\ell_a=0}^{N_a-1}\]
  \}_{\ell_b=0}^{N_b-1}
  \].
\end{dmath}
This entails a four-step algorithm:
\begin{enumerate}
\item Compute $N_b$ length-$N_a$ FFTs
\item Perform a pointwise multiplication with the $N_a\times{}N_b$
  matrix $\[e^{\frac{-2\pi{}iN_aN_b}{N}}\]$
\item Transpose $N_a\times{}N_b\rightarrow{}N_b\times{}N_a$
\item Compute $N_a$ length-$N_b$ FFTs.
\end{enumerate}
If the individual FFTs still don't fit into a single-pass
implementation, then this technique is replied recursively.

These operations may be fused; the output of the FFTs can be
multiplied by the roots of unity, and the output written in a
transposed format.  Writing transposed data directly to global memory
gives calamatous performance due to strided memory access, but this
can be avoided by making use of LDS memory, though power-of-two
transforms require padding in order to avoid memory bank conflicts.
This gives us the ability to compute FFTs unrestrained by the memory
available to a single compute unit by using global memory to store
intermediate results.  The cost of this method is quite high; since
the FFT is already bandwidth limited, additional round-trips to global
memory are not helping matters.  There isn't a lot of work to keep the
GPU busy while we wait for global memory, and the algorithm
fundamentally requires wavefront and kernel level synchronization.

Assuming that the problem size $N$ is perfectly decomposable, the
number of global-memory round-trips is
\begin{dmath}
  \frac{N T_s}{L_B}
\end{dmath}
which requires an equal number of calls to \lstinline{__syncthreads}.
Note that power-of-two transforms will need padding in LDS to avoid
bank conflicts, can reduce the size of problem that fits in LDS.

\subsection{Non-decomposable Transforms}

One is occasionally presented, in the process of computing FFTs, with
transforms whose lengths are not decomposable into convenient problem
sizes, or perhaps not decomposable at all.  The resistance of these
problem sizes to efficient computation may be overcome by using the
Bluestein algorithm~\cite{bluestein1970linear} which maps an
arbitrary-lenght FFT to a convolution with a chirp function.  By the
convolution theorem, this convolution can computed in turn by two
forward FFTs, a Hadamard product, and an inverse FFT; the advantage
being that the FFTs must be performed on data which is padded from
length $N$ to \emph{at least} $2N$.  This gives us the freedom to
choose a more amenable problem size; for example, one may choose the
smallest power of two that is at least as large as $2N$.

The Bluestein method is an effective fall-back method, allowing one to
compute arbitrary-length FFTs with the same scaling and accuracy as
conventional FFTs.  However, it is at about five times as expensive as
a typical FFT, and these problem sizes are generally avoided in
practice.  Small problem sizes that can, a priori, be computed using a
single SIMT thread's VGPR file cover the first 97 primes for
double-precision complex transforms.  Using these as building-blocks,
the proportion of problem sizes up to $2^{30}$ which require a
Bluestein algorithm is only FIXME.  Since the Bluestein algorithm
relies on decomposable FFTs, the benefit for these cases is globally
similar to the decomposable case.

\section{Real/Complex Transforms}
\label{sectionrealcomplex}

Applications of Fourier transforms typically involve real data.  While
the Fourier transform is inherently complex-valued, we can still
reduce the cost of the real/compex FFT by making use of the Hermitian
symmetry inherent in the output of a real-to-complex FFT.  The
simplest way to compute a real-to-complex FFT is to simply compute a
complex FFT where the input has zero imaginary part.  For even-length
transforms, a pre- or post-processing stage allows for efficient and
numerically robust computation.  An even-length real-to-complex
transform is performed by first performing a half-length complex FFT
where the even-indexed and odd-indexed real values are treated as the
real and imaginary parts of a complex input, producing
$\{Z_k\}_{k=0}^{N/2-1}$.  Then a post-processing stage performs the
final pass to create the $N/2+1$ output values by computing
% FIXME: ref?
\begin{dmath}
  \label{rcpost}
  F_k
  = \frac{1}{2}\(Z_k + Z_{\frac{N}{2}-k}^*\)
  + e^{\frac{-2\pi{}k\ell}{N}} \frac{i}{2}\(Z_{\frac{N}{2}-k}^*-Z_k\),
\end{dmath}
where ${}^*$ denotes complex-conjugation.  A similar pre-processing
stage is used to perform the inverse operation.

Another method for performing real/complex when there are an even
number of transforms is to combine two real inputs into one length-$N$
complex input and perform a post-processing stage to seperate the
desired outputs.

The complex-embedding and paired transforms require a length-$N$
complex FFT, the performance of which was discussed above.  Since the
length-$N$ complex-valued data has twice the memory footprint of the
length-$N$ real-valued, the paired and embedded real/complex
reduce the cache and LDS efficiency from what one would a priori
expect for a length-$N$ real/complex FFT.

On the other hand, the even-length transform requires a length-$N/2$
complex FFT, which fits better in cache and LDS.
Equation~\eqref{rcpost} does, however, have a complicated data flow
diagram.  For single-pass transforms which communicate the data in one
step, combining the complex half-length FFT and the post-processing
stage is relatively straightforward.  The data depdency graph for the
pre/post-processing stage imposes a constraint on the data layout for
multi-stage 1D FFT.  Since element $k$ needs and element $N-k$ need to
be processed together, each CU needs to process two of the sub-FFTs in
equation~\eqref{N1N2}. While this increases the per-CU data load (and
hence register pressure / LDS requirements), it allows one to fuse the
complex-valued half-length FFT with the pre/post-processing
real/complex step, thereby eliminating a global-memory round-trip.  In
practice, users are very rarely interested in odd-length FFTs, so
optimising the even-length case is of much greater practical
importance.

The pre- and post-processing passes require that two sets of the data
be present.  For problems that fit entirely in LDS, this is easy to
achieve.  For problem sizes where the half-length complex FFT requires
multiple passes, we require that the decomposition is such that
$N_a T_s \leq L_B$ and $2N_b T_s \leq L_B$.  In effect, this is just
a rebalancing of the data decomposition, so we again have
\begin{dmath}
  \frac{N T_s}{L_B}
\end{dmath}
global-memory round-trips.
  
\section{Multi-Dimensional Transforms}

entire multi-dimensional FFT with just one wavefront. For larger
problem sizes, the current state-of-the-art involves computing these
batches separately.  In order to maintain efficient global-memory
access patterns, the data is transposed between batches.  Each series
of one-dimensional transforms follow the cost model described in

\section{Alternatives to LDS}

The parallelism offered by SIMT architectures needs to be balanced
with effective inter-thread communication for algorithms that are not
embarassingly parallel.  Shared memory is a CU-level explicitly
managed cache which offers good performance with general access
patterns (modulo bank conflicts); the canonical use is to transpose
data at the CU level so that read/writes to global memory are
contiguous.  We also have two or three automatically managed caches
between the CUs and global memory, and an FFT algorithm designed to
take advantage of these caches may be able to take advantage of
various levels of cache in order to share data withing and between
CUs.  Since the L1 to L3 caches are implicitly managed, it's more
difficult to predict the performance of an FFT implementation when
relying on these cache levels.

Cross-lane
operations~\footnote{\href{https://gpuopen.com/learn/amd-gcn-assembly-cross-lane-operations/}{gpuopen.com/learn/amd-gcn-assembly-cross-lane-operations}}
offer another avenue for communicating data between SIMT threads
within a CU.  Cross-lane operations take advantage of register
bandwidth, offering performance advantages over LDS-based
implementations.  Since the \lstinline{ds_permute_b32} operations work
on 32 bits, communicating 8-byte values (such as \texttt{double} or
\texttt{float2}) or 16-byte values (such as \texttt{double2}) requires
multiple calls.  The development effort for cross-lane operations is
higher than for LDS-based kernels, but the potential benefit is worth
exploring.
